# Сайт с «3Д» слоем поверх запущенного образа

Слой — это файлы раздела (`lib/studio3d`, `app/3d`, `app/api/3d`, тесты `tests/studio3d*.test.ts`) и общие файлы
сайта, которые «3Д» правит. Всё остальное остаётся из запущенного образа: в основной папке рядом лежат чужие
незакоммиченные правки, и тащить их нельзя. Навигацию слой не трогает: ссылка «3Д» уже есть в живом
`app/components/Nav.tsx`, а своя копия общего файла устарела бы и при следующей выкатке затёрла бы чужие пункты меню.

## Общие файлы: правки только в `patch-live.mjs`

Живой код основных публикаций (`lib/publish.ts`, `lib/store.ts`, `lib/publications.ts`, расписания,
TikTok-обработчик) — незакоммиченная рабочая копия `C:\Users\user\Desktop\gudini`. «3Д» им пользуется, но меняет
только два места, и обе правки нужны из-за скрытых «зеркал» публикаций (ниже):

| Файл | Правка |
| --- | --- |
| `app/api/projects/route.ts` | список проектов не показывает зеркала (`studio3dId`) |
| `lib/publications.ts` | записи зеркал на странице публикаций ведут на `/3d/<id>` (`lib/studio3d/links.ts`), а не в главный редактор зеркала |

**Где они живут.** Только в `patch-live.mjs` — точные замены строк. `prepare.sh` в момент сборки копирует эти файлы
из основной папки, сверяет их с запущенным контейнером и накладывает правки. Если строка в живом файле изменилась,
правка не ложится и сборка останавливается с объяснением: правку надо пересмотреть, а не накладывать вслепую.

**Почему не в git.** Сами эти файлы в репозитории не те, что работают: живая версия — незакоммиченная копия в
основной папке (`lib/publications.ts` в git даже не добавлен). Закоммитить их правленую копию из ветки «3Д» значит
при слиянии затереть чужую работу. Поэтому в ветке есть только правка (`patch-live.mjs`), а не файлы.

**Сверка с сайтом.** Копия из основной папки должна совпадать с файлом в `gudini-site` (без правки или уже с ней).
Если не совпадает, в основной папке лежат не выкаченные правки — слой отправил бы их на сайт, и `prepare.sh`
останавливается. Пропустить сверку осознанно: `STUDIO3D_SKIP_LIVE_CHECK=1`.

**Когда ветку сольют в master** и сайт будут собирать из основной папки целиком, правки надо один раз наложить на неё
и проверить — иначе зеркала появятся в списке проектов, а их публикации поведут в главный редактор:

```
node studio3d/deploy/site/patch-live.mjs C:/Users/user/Desktop/gudini
node studio3d/deploy/site/patch-live.mjs --check C:/Users/user/Desktop/gudini
```

Повторный запуск безопасен: уже наложенную правку скрипт узнаёт. Копии живых файлов в worktree (`live-files.txt`)
нужны только для `tsc` и тестов: их не коммитят и на сайт не отправляют.

## Сборка

Из корня worktree, в Git Bash:

```
bash studio3d/deploy/site/prepare.sh
docker inspect -f "{{.Config.Image}}" gudini-site
docker build --build-arg BASE=<образ из прошлой строки> -t gudini-gudini-site:3d-<дата-время> studio3d/deploy/site/build
```

Сборка гоняет все тесты «3Д» (публикация и ссылки страницы публикаций проверяются против кода этого же образа) и
`npm run build` с проверкой типов: при ошибке образа нет. Перед выкаткой ещё раз сверить `docker inspect gudini-site`
— сайт могла пересобрать другая сессия.

## Публикация «3Д»

Видео «3Д» публикуется через скрытый основной проект — «зеркало» (`lib/studio3d/publish.ts`): у него поле
`studio3dId`, состояние «готово», в его папке — ссылка на `out.mp4`, `cover.jpg` и файл `studio3d-mirror.json`
(какое видео лежит и какое ушло в каждую сеть). Так TikTok-обработчик, YouTube, Instagram Reels, черновики,
расписания, пробные Reels, отмена и страница публикаций работают без изменений.

После удачного монтажа сайт сам, в фоне, пишет описание и рисует обложку, если их ещё нет (одна платная
картинка). Выключить: `STUDIO3D_AUTO_PREP=off` в окружении сайта. Расходы на обложку и описание видны на странице
«Расходы» с пометкой «(3Д)» и названием ролика, без ссылки: ссылка там ведёт только в главный редактор.
